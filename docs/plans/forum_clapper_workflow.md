1. 总目标与基本分工

目标是用现有 ChatGPT 和 Claude 订阅，持续交付经过验证的完整行为，减少碎片派单、重复分析和反复交接。

Sol：

- 负责普通独立源码审核、运行证据核验。
- 统一调度正式性能测量和实机实验，负责停止、清理和结果登记。
- 实现期间重点处理影响方向、接口和验收条件的问题，不与 Opus 重复实现同一功能。

Opus：
- 负责工作包的具体设计、源码实现、必要测试、离线调试和修复。
- 负责构建能够经过真实生产路径的验证场景及测量入口。
- 对交付质量负责，先自行验证，再提交独立审核。
- 审核或实机发现问题后，继续在原工作包内定位、修复和验证。

Astra Extra High：
- 负责重要阶段方案、关键假设检查、重大分歧裁决和关键审核。
- 按明确问题调用，避免参与日常派单、普通收据核对和重复材料整理。
- Astra 的意见需要证据支持；Sol负责落实，并如实保留尚未验证的判断。

同一工作包原则上只有一个实现负责人。默认由 Opus 实现；确需改由 Sol 实现时，明确交接，该包的独立审核交给 Opus 或 Astra。

4. 按完整行为建立工作包

一个工作包应能描述“什么情况下，系统应该完成什么行为，以及怎样证明”。

例如：
“修复目标姿态变化导致的第三刀打空，验证命中判断及失败后的恢复。”
不要拆成“改三行→审三行→补夹具→审夹具→核收据”等多个独立任务。

每个工作包只保留一份简短任务说明：
- 目标行为及当前失败证据；
- 范围和必要约束；
- 实现负责人、独立审核人；
- 相关源码、数据和已有可复用工具；
- 离线验收、性能验证、实机验收分别需要什么证据；
- 完成条件与尚未覆盖的边界。

给 Opus 实现判断空间。可以明确不变量和接口约束，不要在尚未查清根因前预设“只能改某三行”。

一个工作包使用一个主任务编号。普通补充、修订和审核反馈留在该编号下。
只有目标或验收范围实质改变时，才拆出新工作包。

优先推进一个核心行为包。只有依赖和文件修改互不冲突时才并行。
普通“已收到”不触发新一轮任务或唤醒；实质交付、阻挡和状态变化再通知。

5. Opus 的实现与离线验证

Opus接单后：
- 先核实失败发生在哪条真实执行路径；
- 检查计划中的假设，发现不成立就带最小证据反馈；
- 完成实现、必要测试和离线调试；
- 将修复直接落在约定的开发分支/工作树，交付可审核的提交或补丁。

Sol优先集成已审提交，避免把Opus的原型重新手工实现一遍。

测试重点：
- 复现原失败，并验证新行为；
- 保留相关成功场景，防止修好一个点破坏已有路径；
- 对本次改动涉及的危险边界补有意义的反例；
- 验证真实生产接口，不用只适用于单测的输入冒充生产输入。

优先复用并修正统一的生产输入夹具，特别核对：
- StateTracker/ChainSim的真实数组形状；
- OracleBackend实际提供的FSM和状态字段；
- HERO2及其他实际生效配置；
- 真实地形、坐标系和朝向；
- 身体运动与状态时钟是否一致；
- 已发送、待生效和当前锁存输入。

按需要经过真实的policy、planner、预测/几何、before_send和sent路径。
验证新增分支确实被执行，不能仅凭helper返回正确就宣布完整行为通过。

回放从首次动作分歧后，不能继续把原录像后续状态当作新策略的自然闭环。
合成输入、预置Run、模型命中和实机观察必须明确区分。

通过相关检查后停止重复测试。只有新改动、新失败或未解决风险才扩大验证。
不要为了一个局部修复新造完整模拟器或无边界测试矩阵。

6. 交付、独立审核与修复

Opus一次交付一个可审核的包：
- 源码版本/补丁；
- 解决的问题和行为变化；
- 关键测试及生产路径证据；
- 性能测量入口和目标分支覆盖情况；
- 已知限制、未验证项；
- 建议的下一步。

材料尽量引用已有产物；机器可核的版本、配置和文件绑定由脚本完成。

Sol先检查交付是否足以审核，再进行独立源码审阅。
普通改动由Sol审；涉及关键模型假设或重大行为变更时，调用Astra承担相应重点审核，避免双方重复做同一套全面审阅。

审核重点：
- 是否解决目标问题；
- 实现依赖的假设是否符合生产输入；
- 实际动作所有者、发送、接受、命中和交接是否一致；
- 是否遗漏其他敌人、延迟危险或失败恢复；
- 测试是否真正经过修改的分支。

发现问题时，给出位置、触发条件、证据和影响。
Opus在同一工作包内修复，审核只跟进相关增量和必要邻接路径。

影响目标行为或运行条件的实质阻挡未解决时，不签通过。
无关改进进入后续队列，不顺手扩大当前工作包。

7. 正式性能测量

Opus负责准备并跑通功能场景；Sol统一执行正式性能测量。

先证明：
- 输入和配置有效；
- 目标分支实际被触发；
- 完整路径功能成立。

之后再测量性能。不要先测两个方便取得的旧点，再把它们当作新增功能的预算。

正式测量继续遵守项目现行资源、线程、独占、暂停和清理规则。
测量期间由Sol协调Opus及其他计算任务，避免相互干扰。

报告明确区分：
- helper/组件耗时；
- 完整_act或完整tick耗时；
- 冷启动与热路径；
- 有限场景测量与全场、实机截止时间保证。

超预算、冷启动慢帧和测量失败如实保留。
不能把不同场景的片段相加，当作完整关键tick通过。

源码、配置或关键输入变化后，重新核对证据适用性，只补受影响的验证。
正式性能结果并入原工作包，不为每份收据另开一次任务。

8. 实机验收

实机由Sol统一调度执行，Opus负责分析结果和修复。
只有Sol明确交接执行责任后，Opus才接管实机；同一时间只保留一个实机控制负责人。

开局前确认：
- 当前候选已通过所需独立源码审核；
- 相关生产路径和性能证据成立；
- 运行源、模型、实际配置、输入链路和测量日志绑定正确；
- 实验在已有用户授权范围内；
- 局数、停止条件、资源和清理流程已明确。

已有明确授权的有界实验直接按授权执行，不每轮重新问我。
超出授权范围时，先完成可独立推进的准备工作，再明确指出需要决定的具体事项。
本workflow本身不增加局数、不放宽停止阈值、不解除旧NO_RETRY或暂停状态。

运行中沿用现行掉血、死亡、输入失步、关键日志缺失等停止条件。
发生停止后保留原始记录，完成真实退出和清理核验，再解除忙碌状态。
不能只凭状态文件写成false，就认为所有进程已退出。

实机结果必须记录：
- 目标行为获得多少次机会，实际发生多少次；
- 最终动作所有者及实际发出的按键；
- 输入接受、命中、弹起和真实交接；
- 全战斗及退出阶段的HP损失与来源；
- 配置、日志和清理完整性。

没有实际触发目标路线，应记为“未覆盖”。
少量成功只支持相应范围的结论，不直接宣布稳定、无伤或优于基线。

9. 失败后的处理

先建立事实链：
当时输入和状态 → 实际动作所有者 → 发送与接受 → 命中/弹起/交接 → 后续伤害。

先区分是：
- 规格或模型假设错误；
- 实现错误；
- 夹具/配置错误；
- 测量或日志问题；
- 场景未覆盖；
- 证据不足。

不要在归因前预设是“普通planner的问题”或“某个入口太保守”。
Opus给出最小复现、修复及相关验证；Sol维持同一工作包跟进。
若证据推翻阶段方案，再调用Astra处理重大假设变更。

相同类型的问题反复出现时，修正共用接口、模型假设或夹具，沉淀已有事故回归，避免不断增加单例补丁。

原始失败数据不修改成通过。更正结论单独记录。
新实验需满足当前授权和更新后的运行条件，不能把修复一个无关字段当作重跑旧失败局的理由。

10. Astra和订阅额度控制

Astra默认集中用于阶段方案及关键审核，不逐补丁调用。
同一次审核尽量合并相关源码、功能证据、性能边界和待决策问题。
如果Astra已完成关键源码审核，后续普通证据核收由Sol完成；新增事实改变结论时再补充询问。

交给Astra的资料以当前事实、关键争议、改动和证据路径为主。
允许它按需读取原件，避免复制整份历史邮件或全部日志。
Sol不同时重复开展已经交给Astra或Opus的同一项分析。

按完整工作包记录：
- ChatGPT与Claude可取得的额度变化；
- 完成时间、返工轮次；
- 通过了哪些验收，遗留什么问题。

额度变化需注明统计窗口及同期其他任务，不能把账户总消耗全部归到一个工作包。
拿不到某一方用量时如实标未知，不编造token或费用。

根据剩余额度、距刷新时间和有效产出调整后续任务。
额度偏紧时，优先减少重复上下文、碎片交接和不必要的高强度调用；必要时明确移交下一完整工作包的实现责任。
不要为了节省额度降低验证真实性，或提前把任务标为完成。
