## 0. 一页结论

- **控制器不换**：保留旧规划器（h2 = rnjb + HERO2）的同步 tick（500 行 × 36 帧，决策 p50 约 8 ms）。新东西只能以"候选行"或"打分项"的形式进去。map2 不作为控制器。
- **现在缺三样东西**：
  1. 1–3 s 的站位判断。双 Clapper 的头号死因是被另一只的跳落 / 大符文逼死，而陷阱在跳跃那只 Jump Aim 的时刻就已经设下（SP14 查过，不是规划器 bug）。
  2. 刀口路径接不住脚本的出刀。开环回放里，在 SLAM_PLAY 自己的站位上只劈中 25/47 次锤，脚本是 45/47。第 1.1 步查明表本身不缺格（脚本起手帧 92.9 % 落在 FULL 格），卡在按键路径：接近行只有 `drop_slam0`、固定交权帧把窗口截掉、钩索的按键校验和表不一致、后台检查有延迟。25/47 是开环数，录像一分叉回放就判断不了，不等于闭环劈中率。
  3. 每帧保退路。拆分实验按固定帧交权，没有哪个交权帧能既保住退路又能出刀。
- **现成但没用上的东西**：旧规划器已经有终点价值 `combat/terminal.py`（E / trapped / overlap / H_exp，可达模板看到候选终点后 1.4 s）。它 10-08 只在第 0 波（多种敌人）上用身体场测过，闭环没有收益，之后默认关（`SSBOT_FORUM_TV`），**从没在 Clapper 波上测过**。所以"站位分的逃逸项"第一件事是在 Clapper 波上复核它，而不是新写一个 V(x)。
- **顺序**：第 0 步 测量协议 → 第 1 步 两个离线差集 → 第 2 步 终点价值上 w13 → 第 3 步 刀口行内联 + 每帧保退路 + 起跳接近行 → 第 4 步 机会项、四条规则、按家族退规则 → 第 5 步（按需）递归表量化重建。

## 2. 硬约束（每一步都适用）

- 时间结构不动：旧规划器的同步 tick，单线程每 tick ≤ 8 ms。
- 不准出现提交、交接、兜底、后台 worker 发 Press。所有出刀都是同步 tick 里的普通候选行，走旧规划器同一套检查（两段检查、命中分支、escape-ready）。
- 先离线、后实机。每一步一个闸门；闸门失败就停，等你决定，不在失败上继续往上盖。
- 一次只改一处，和 h2 配对比；报告里每个数都和 h2 并排。
- 每一步开工前写一页规格：离线产出什么、每个 tick 做什么、闸门是什么。你看过再开工作流。
- 每个阶段都审计掉血原因和漏掉的计划动作（没劈的锤、没打的 Idle），包括开关之间的冲突。

**A 类：根本没给窗口（L2 11，SP14 14）**

**审阅意见（Opus 5.5，10-27）**
1. 开环回放的边界：录像一旦走了拆分方案不会走的动作（CLAWSTRIKE 出钩、SLAM_PLAY 提前侧劈），后面的状态就不是拆分方案会走到的状态，回放只能拒绝。B1 的 16 次、A1 的第 2 条、B2 的大部分都是这种情况：56 次差集里有 20 多次是开环判断不了，不是刀口路径失败。所以 25/47、35/85 不是闭环劈中率，第 6 节的离线闸门改成闭环。
2. 钩索校验往哪边改要先查。`FREE_MIN = 10` 是实机验过的（S1b 54/54），也可能是表乐观了一帧，而不是校验太严；9.00036 帧的取整看起来是真的浮点 bug。改之前，先在实机 CLAWSTRIKE 劈中的那些锤上（L2 17 次、SP14 17 次）量出游戏实际在控制后第几帧接受攻击，再改错的那一边。盲目放宽校验，可能按出一个游戏不认的下劈，她会直接落到 Clapper 身上。
3. `oldwin_press.py` 的注释记着，V1 里 `hop_slam0` / `pogo_head2` 的接近按键"晚一帧就被否定"。同步路径没有桥接延迟，可能正好解决，但新加的起跳接近行要重新验证，不能默认可用。

**修法清单（第 3 步的输入）**

### 4.2 被困差集（SP14 的被逼局面：跳落 10、大符文 7，以及 JUMPTRAP 之后的小符文 19）

- 在每个局面之前 0.5–2 s 的每个 tick，离线跑现有的 `TerminalValue`，用两种场各跑一遍：
  - 身体场：10-08 上线的形式，启发式；
  - 支撑场：用 Clapper 的预测建场。如果旧规划器的 `MultiForecast` 对 Clapper 的支撑也饱和，就改用 map2 的 L1 模型的危险区间来建。
- 看三件事：
  1. 场是否饱和：每个时间格被覆盖的格子比例。第 0 波是 100 %。
  2. 在 Jump Aim 那一刻，`trapped` / E 是否已经把"会被关门"的站位区分出来。
  3. 那时候的候选里有没有不被困的行。有，说明终点价值能救；没有，说明要更早看出来，或者要加瞄准引导。
- 产出：一张表，列出每个局面、最早能看出被困的时刻、当时是否有不被困的可选行。**闸门**：能看出且有可选行的局面过半，才进第 2 步。否则先补第 4 步里"按她的位置枚举 Clapper 选招"的那一项。

## 6. 第 3 步：刀口行内联 + 每帧保退路 + 起跳接近行（先做单怪）

- 按第 4.1 节的修法清单改。接近行的重点是 `hop_slam0`：停步约 5.6 u 后的 j = 24、25，以及空中入场的版本。她在 6–7 u 时脚本用的是钩索（CLAWSTRIKE），对应 `claw_slam0`；钩索的按键校验先和表对齐（第 4.1 节审阅意见 2）。

## 7. 第 4 步：机会项、四条规则、按家族退规则

- **机会项**：在终点价值里给"能接上刀口"的终点加分。对每只 Clapper，按 L1 模型、随她的位置去枚举它的下一招（近招还是远招；跳是约 8.4 u 以外才出的远招，见 `forum_planner_plan.md`），再看从终点能不能赶上那一招的刀口格。决策帧之后的伤害取决于她的位置，所以这里要按她的位置枚举，不能对所有选择取并集，否则场又会饱和。
- **四条双怪规则**（你的原话，`forum_map_v2.md` 约 1304 行）：
  1. 站在两只之间；
  2. 在两只之间时，打离它身后那面墙更远的那只；
  3. 两只必须在同一侧时，把它们压进墙角，自己绝不被压；
  4. 两只离得远时，把焦点怪往中间赶。

## 8. 第 5 步（按需）：递归表量化重建

- **触发条件**，满足任一才做：
  - 第 2 / 4 步的回放显示，可达模板（按终点类别的粗模板，看终点后 0.2 / 0.5 / 0.9 / 1.4 s）在空中终点、冲刺已用、钩索这些情况下判错，而且影响到了选择；
  - 500 行 × 36 帧明显漏掉了可行的刀口或退路。
- **不为提速而做**：实机控制器不用递归表；在 map2 里包络只占一次决策的 19 %，单独重建最多快 1.2–1.3 倍。它真正的用处是 1–2 s 的快速可达查询，给站位判断用。
- **方案要点**（Fable 5.1，10-26）：
  - 键量化：竖直相位、vx 分格、格点外 vy 分档、中途状态记成"动作 + 第几步"；
  - 值带区间：内区间对格内每个成员都成立，外区间盖住所有成员；
  - 地形不进键，每帧对高度区间做切割；
  - 可达、伤害、刀口三张表共用一套键；
  - 四级离线验证：可靠性（内 ⊆ 精确 ⊆ 外，0 违例）→ 封闭性（520 局回放，热身后每次决策新节点为 0）→ 完备性损失（在 235 个情境的验收集上，取损失 ≤ 1–2 % 的最粗格宽）→ 速度（36 步带伤害切割的前推 ≤ 1–2 ms）。
