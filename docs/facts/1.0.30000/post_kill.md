## 1. 击杀之后还有什么是活的（录像）

全部 Bell Beast 录像（数据、oracle / 视觉视图 eval、注入），4,603 次击杀（Control → Death Broadcast），每次看到下一次读档前房间的最后一帧（读档会重载 Bone_05 本身，房间的帧到 scene_leave 为止）。"活的" = `train.episode.live_threats`：启用的伤害碰撞体（eff > 0、can_cause_damage），或已武装、稍后才伤人的危险物（落铃的 Antic）。

| 击杀时 Boss 的状态 | 次数 | 击杀后活着的 |
|---|---|---|
| Burst Out | 1,140 | **全部**：两颗攻击铃（L、R），击杀那一帧已在 Launch / Launched Up |
| Dig In | 545 | 114 次一颗正在下落的落铃（DropBell M2，Air） |
| Descending / Leap Land / Leap Out / Charge / Charge Antic / Charge Emerge / Charge End | 1,368 / 759 / 478 / 231 / 25 / 34 / 23 | 没有 |

- **攻击铃不受 Boss 死亡影响**：照样飞完、落地、滚动（vx 12），直到 End Timer（首次触地后 2 s）。从击杀后第一帧的位置和速度用注册表物理推演（`pogo_targets.simulate`），2,280 颗铃、击杀后录到的全部帧，在预测的时间余量带（±0.04 s）内中心误差最大 **0.032 u**（p99 0.031 u）。录到的最后一次接触在击杀后 207 帧。
- **Antic 中的落铃被取消**：Boss 死亡那一帧，处于 Antic 的落铃 FSM 进入 Cancel，1,222 次，**全部在击杀帧**，没有一次离开 Cancel：不会落下。正在下落的（Air 及以后）照常落地、弹起、沉下。
- **本体**：Boss 死后本体碰撞体最多再伤人一个物理步：击杀后的 82 次本体接触（71 次 damage_blocked、11 次 damage）都在击杀后 10 帧内、**游戏时间 ≤ 0.0202 s**。死亡的 Boss 不在导出里（state_fields_m2.md），所以这些接触只能从事件看到。
- 击杀后的其余受击事件都是注入的（暂停压力测试，61 次）。没有别的伤害源。

## 2. Boss 死后的预测（`combat/forecast.py`，代码 5a97e0f）

- 以前：死亡后推演没有根节点，只放"被打断攻击的尾巴"（`_tail` 模板，death_tail）。BB_BURST 的尾巴模板是从攻击**正常结束**算起的攻击铃并集（铃在滚），却放在死亡时刻；被杀的那次铃爆的铃还在上升，所以这段预测既放错了时间，也不覆盖之后的飞行和滚动。
- 现在（oracle 视图）：Boss 死后，导出里每颗碰撞体还开着的攻击铃都按精确路径进支撑（DetBell：当前位置、速度、注册表物理；寿命 = 首次触地 + 2 s + 0.05 s 余量，还没触地的在 2 s 视野内不结束），两颗都在精确路径上时不再放 BB_BURST 死亡尾巴里只含攻击铃的那部分（`SSBOT_DEAD_ATK=0` 恢复旧做法）。落铃照旧按"已武装"跟踪，Cancel 算静止（`REST_STATES`），被取消的铃不再留在支撑里。Boss 活着时不变。
- 支撑召回（`support_recall`，oracle，L = 3，余量 0；三次留了 2.5 s 击杀后录像的注入运行 20261004_041626 / 042718 / 043850）：

| | 全部接触 | 未覆盖 | 其中击杀后（Death Broadcast 之后）的攻击铃 |
|---|---|---|---|
| 旧预测 | 424 | 158 | **104**（全部） |
| 新预测 | 424 | 54 | **0** |

  两边剩下的 54 次都是注入的受击（Hero_Hornet 源，不是真实接触）。
- **认证用的支撑本来就含这些来源**（`post_kill cover`）：同三次运行里击杀后的 105 次真实接触（104 次攻击铃、1 次本体），全部被**击杀前一帧**（Boss 还活着，2 s 视野，即击杀一击认证所用的预测）覆盖，接触在该帧之后 0.017–1.116 s；也全部被死后 L = 3 帧的新预测覆盖。所以认证窗口（击杀 + 慢动作 + 0.15 s）和整条计划（S = 0 到推演结束）检查的支撑里有这些铃；以前的缺口在窗口**之后**：死后预测没有它们，规划器照着空支撑走进了铃。

## 3. 规划器在死后继续控制（`train/planner_policy.py`、`train/episode.py`）

- PlannerPolicy.act_after_clear = True：收尾期间每帧照常 tick（以前注入运行靠 HitInjector 的同名开关，普通运行击杀后 60 帧发零键）。
- 死亡慢动作：有击杀承诺的按承诺走（pause_quit.md 10.3）；**没有承诺的死亡**（I3 自己的 HP 条件下的一击：满血 h ≥ 3）把最后一个 tick 发出的计划同样按游戏时间执行到击杀窗口结束（`_post_kill_commit`，记 certified False、post_kill True），之后规划器照常 tick。理由同 10.3：慢动作里每个游戏帧约 20 次 Update，逐实时帧重规划会松跳、让上升立刻停止。
- 开环回放（新代码驱动 043850 的 5 场录像，击杀后 150 帧）：1 次走 `_post_kill_commit`（回放里的选择与实战不同）、4 次经认证承诺；承诺之后 35–54 个规划 tick 全部 S = 0，0 次 FORCED_RISK，无异常。

## 4. 评估的收尾（`train/episode.py`，`Encounter.tail_quiet_s`）

- Bell Beast：击杀后一直跑，直到连续 2 s **游戏时间**没有活的伤害源（每个 STATE 都看，读者线程的 FightTap 计时；慢动作 0.167 s 游戏时间约 100 实时帧也照游戏时间算）。离开房间也结束（记 `tail_end`）。收尾超过 15 s 记 STUCK。
- 收尾里挨打照常计数（`tail_hits`、`tail_hp_lost`，也在 `hits` 里）；致命的记 WOULD_DIE；收尾结束前监督器退出记 **QUIT**（"quit after the kill"，以前记 CLEAR）。
- 新字段：`kill_s`（醒来到击杀，汇总的击杀用时改用它）、`f_kill`、`tail_s`、`tail_threat_s`（击杀到最后一个活来源）、`tail_threats`、`tail_end`。汇总多一节 `post_kill_tail`。
- 没有任何来源时收尾 = 2.015 s 游戏时间（实时约 3.3 s，含慢动作）。`SSBOT_POST_CLEAR_S` 仍是固定窗口（会关掉收尾，只用于录整段慢动作）。

## 5. 过去的 CLEAR 会怎么变（`post_kill clears`）

过去的 eval 在击杀后 60 帧结束，录像再多十几帧，都还在慢动作里（击杀后约 0.07 s 游戏时间）。对每个 CLEAR：录到的最后一帧有没有活的来源（新规则下收尾会更长），以及"原地不动的主角"（旧测试框架击杀后发零键）会不会被这些来源打到：从最后一帧推演到 End Timer（落铃两个弹跳方向都算），对最后的受击框（在空中则落到地面）。不算受击无敌和慢动作里的移动，是暴露量的估计，不是回放。

| 运行 | CLEAR | 窗口结束时还有活来源 | 原地不动会挨打 | 其中当时 HP ≤ 3（挨打后 h ≤ 1） | 其中会致死（HP ≤ 2） |
|---|---|---|---|---|---|
| oracle eval（60 次运行） | 2,878 | 772（Burst Out 671、Dig In 101） | 714 | 0 | 0 |
| oracle 注入（25 次运行） | 224 | 27 | 19 | 7 | 6 |
| 视觉视图 eval（41 次运行） | 1,253 | 361 | 359 | 0 | 0 |

- 普通 oracle eval 的 CLEAR 里没有一次在不满血时击杀，所以新规则下**没有一个会改判**（最多是收尾里挨一下 2 格，h 3 → 2）；但 26.8 % 的收尾会比 60 帧长，24.8 % 在旧做法（不动）下会挨打。规划器继续躲之后实际怎样看第 6 节。
- 注入运行（暂停压力测试，击杀前后注入受击到 1 HP、或注入退出 QF）：**106 个过去的 CLEAR 是"击杀后退出"**（67 次 Q1、39 次注入的 QF），新规则下全部改判 QUIT；其中 6 次是死后攻击铃造成的 Q1（042718 2 次、043850 4 次，pause_quit.md 10.3）。按原地不动估计，另有 7 个 CLEAR 会在收尾里挨打（6 个致死：WOULD_DIE，1 个 Q1：QUIT）。
